# Dictation in agent chat

On desktop, the microphone replaces the composer with a recording view. A volume meter beside the microphone and a waveform spanning the input show the actual microphone signal; the timer shows recording duration. The controls use the app's existing compact button sizes and theme colors.

- **Enter / Send:** stop capture, wait for the final transcript, and send the text through the existing chat submission path. A working agent queues the message as usual. Empty dictation never sends an existing draft or attachment by itself.
- **Stop:** finish capture and show the transcript for review without sending.
- **Edit:** finish capture and return the text to a focused, editable composer.
- **Cancel / Escape:** discard the current dictation and restore the draft from before recording. Existing attachments remain.

Dictated words update the session's existing draft storage while recording. Switching tabs, hiding the app, disconnecting, or closing the composer releases capture; a pending Send cannot deliver after leaving the tab or disconnecting. Recognition errors and a finalization timeout (5 seconds for a browser speech service, 30 for the daemon) keep captured words available for review, without sending automatically. Late callbacks from a canceled recording cannot overwrite a newer draft.

The waveform uses a local Web Audio analyser at up to 20 samples per second. A separate microphone stream is used only for metering; every track and audio context is released on completion, cancel, failure, or unmount, including when permission arrives after cancellation. If metering is unavailable, transcription can continue and the meter reports that its level is unavailable. Reduced motion hides the scrolling waveform history while retaining the live level meter.

## Where transcription runs

The daemon hosting the agent transcribes, so dictation works the same in every desktop webview, including WebKitGTK and WebView2, which have no speech service of their own. On a cloud machine, the machine transcribes; for a local agent, it's the laptop's bundled daemon. Audio goes only to that daemon.

- **Protocol.** Daemons advertise `dictation-v1`, and clients declare it in `client.hello` before any dictation event reaches them. The client sends `dictation.request` (`start`, `finish`, `cancel`, `status`, `prepare`) and 16 kHz mono 16-bit PCM in `dictation.audio` chunks of at most one second, numbered from 0. The daemon answers with `dictation.transcript` (the whole text so far; `final` once) or `dictation.error`, and broadcasts `dictation.model` when the model's availability changes. A gap in the numbering ends the recording with an error instead of transcribing garbled audio. Recordings stop after 10 minutes and end when their connection closes.
- **Engine.** [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx) runs NVIDIA Parakeet TDT 0.6B v2 (int8, English), the same setup Paseo uses by default. Audio is split into utterances at pauses and transcribed once each, in order. The unfinished utterance is re-transcribed about once a second as a preview. Utterances too quiet to be speech are skipped rather than transcribed into stray words. The recognizer runs in a `concors-speech` child process of the session host (`concors-daemon speech-worker`). It takes about 1.2 GB while loaded, and the addon never frees that memory, so the worker exits after ten idle minutes and restarts on the next dictation. A native fault ends the worker, not the session host and the agents and terminals it holds.
- **Model.** About 660 MB, downloaded in the background shortly after the session host starts. The files are pinned to one Hugging Face revision and verified by SHA-256 before they are used. They are kept in `<data dir>/models/speech`, shared by every profile on the machine. The download needs roughly 1.2 GB free, retries every five minutes after a failure, and while it is running the microphone button explains the progress instead of recording. The model is [`csukuangfj/sherpa-onnx-nemo-parakeet-tdt-0.6b-v2-int8`](https://huggingface.co/csukuangfj/sherpa-onnx-nemo-parakeet-tdt-0.6b-v2-int8), a conversion of [nvidia/parakeet-tdt-0.6b-v2](https://huggingface.co/nvidia/parakeet-tdt-0.6b-v2) under CC-BY-4.0.
- **Packaging.** `sherpa-onnx-node` and its platform addon sit beside the bundle like the PTY module, because esbuild cannot inline a native addon. The bundle smoke test loads the addon with the shipped Node, so a glibc or rpath problem fails CI rather than a user's dictation.
- **Microphone access.** WebKitGTK denies `getUserMedia` unless the embedder answers its permission request, so the Linux shell grants audio-only capture to the app's page (`src-tauri/src/microphone.rs`). Camera and screen capture remain denied. macOS asks the user, using the usage text in `src-tauri/Info.plist`.
- **Fallback.** Daemons without `dictation-v1` (older releases, ephemeral and test daemons) use the webview's SpeechRecognition where it exists, as before; elsewhere dictation stays disabled. Mobile retains OS keyboard dictation.

Real microphone hardware and OS-specific audio stacks need manual device verification. Automated coverage uses deterministic speech events, microphone samples, and a fake transcriber.

Implementation references: [SpeechRecognition.stop](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition/stop) and [AnalyserNode.getFloatTimeDomainData](https://developer.mozilla.org/en-US/docs/Web/API/AnalyserNode/getFloatTimeDomainData).

Tests: `dictation-session.test.ts` covers finalization, cancellation, errors, stale callbacks, timeouts, and draft limits. `dictation-daemon.test.ts` covers resampling, PCM encoding, streaming order, daemon errors, denied microphones, and cancellation. `dictation-audio.test.ts` covers measured volume and capture cleanup. In the daemon, `src/dictation/*.test.ts` cover model download and verification, utterance segmentation, transcript ordering, ownership, and capability gating. `e2e/dictation.spec.ts` covers Enter, Edit, Stop, Cancel, permission failure, tab changes, reduced motion, and narrow layouts; the existing composer journey covers attachments and queued-message integration.
